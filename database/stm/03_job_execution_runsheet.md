# Deliverable #3 — Job Execution Run Sheet

**Machine-readable companion:** `database/stm/job_execution_runsheet.csv`
(67 rows, 14 columns), regenerated by
`backend/scripts/stm/generate_runsheet.py`.
**Guarded by:** `backend/tests/test_runsheet_is_not_fabricated.py` (6 tests).
**Evidence:** `database/stm/lineage.json` — 242 modules scanned, 142 touching
the database.

This document says what runs, in what order, what each step depends on, and
which steps may run at the same time. The CSV is the authority for the
per-row detail; this page explains the structure and the parts of it that are
easy to misread.

---

## 1. Four kinds of execution, and they are not the same

| Cadence | Rows | What governs order |
|---|---|---|
| `daily` | 15 | shell pipeline, top to bottom |
| `weekly` | 15 | shell pipeline, top to bottom |
| `monthly` | 2 | shell pipeline, top to bottom |
| `plan:DAILY_CANONICAL` | 7 | the canonical driver, under an execution lease |
| `plan:FULL_FUNDAMENTALS_CANONICAL` | 8 | the canonical driver, under an execution lease |
| `scheduler` | 20 | APScheduler cron triggers — **no ordering at all** |

The distinction is the most important thing on this page. A step in a shell
pipeline runs because the previous one returned. A scheduler job runs because
a clock said so, and **nothing sequences it against anything else**. Twenty
jobs in that group hold no dependency relationship to the pipeline or to each
other, and the run sheet does not pretend otherwise — their
`depends_on_data` is whatever the lineage shows, not an execution order.

## 2. The daily pipeline

```
 1  Download EOD prices                         (writes no table)  L2
 2  Download ASIC short positions               (unresolved)
 3  Load prices        -> staging_au            Bronze             L0
 4  Load short         -> staging_au            Bronze             L0
 6  Transform short    -> market.short_positions Silver            L1
 5  Transform prices   ─┐
 7  Daily compute       │
 8  Technical compute   ├─ executed by the CANONICAL DRIVER,
 9  Half-yearly compute │  not by this pipeline — see §3
10  Period metrics      │
13  Build universe     ─┘
11  ASX index prices
12  ETF & fund prices
14  Heatmap cache      -> market.heatmap_cache  Gold               L3
15  Market snapshots
```

Steps 5, 7, 8, 9, 10 and 13 appear in the pipeline in numeric order and are
**not run by it**. They are delegated to the canonical driver, which is why
those rows carry no script and no layer — their real execution is the
`plan:` rows in §3. The numbering is a reading aid, not an execution order,
and reading it as one is the single easiest mistake to make with this
document.

Step 2's downloader does not resolve to a module in the lineage graph, so its
data effects are recorded as `(unresolved)` rather than as an empty writes
column. Step 1's downloader does resolve and genuinely writes no table — it
writes files — so it reads `(writes no table)`. Those two labels mean
different things and the CSV keeps them apart.

## 3. The canonical plans — where publication is actually decided

Two plans, declared in `compute/engine/run_plans.py` and executed by
`scripts/p0a_canonical_run.py` under an execution lease.

### DAILY_CANONICAL

| # | Stage | Layer | Required to publish |
|---|---|---|---|
| 1 | `transform_prices` | Silver | yes |
| 2 | `daily_compute` | Gold | yes |
| 3 | `technical_compute` | Gold | yes |
| 4 | `halfyearly_compute` | Gold | yes |
| 5 | `period_metrics_compute` | Gold | yes |
| 6 | `universe_build` | Universe | yes |
| 7 | `composite_score` | Universe | **no — it writes the finalisation** |

`yearly_compute` is deliberately absent and is listed under `reuses`. Its
output is inherited, and a fingerprint check is what makes that legitimate.

### FULL_FUNDAMENTALS_CANONICAL

The same eight stages with `yearly_compute` inserted second and required, so
the plan computes yearly output for itself and inherits nothing.

### Two rules that are easy to get backwards

1. **`composite_score` must be last and must NOT be required.** The plan
   validator refuses a plan that requires it, because it is the stage that
   *writes* the finalisation — requiring evidence from it is requiring
   evidence that cannot exist yet.

2. **The last stage is not dispatched from `STAGE_COMMANDS`.** The driver
   runs `for stage in plan.stages[:-1]` through the command table, then
   invokes `composite_score` explicitly as the canonical commit. Any tool
   reading only `STAGE_COMMANDS` goes silent at exactly the step that
   publishes — this run sheet did, until it was fixed to read the explicit
   invocation too.

### What failure means here

`REFUSE publication` on 13 rows is not the same as `ABORT pipeline` on 14.
A refused publication leaves the previous published universe intact and
serving; the run simply stays unfinalised. That is the design: an
unpublishable run is never downgraded into a published one, and a retry is a
*new* run rather than a second attempt at the old one, because
`compute_run_stages` is append-only with one terminal row per
`(run_id, stage_name)`.

## 4. Parallelism

The CSV's `parallel_level` is derived from the data dependency graph — a job
at level *N* reads nothing written at level *N* or later. Jobs sharing a
level have no data dependency between them and **may** run concurrently.

| Level | Modules | Character |
|---|---|---|
| L0 | 31 | loaders and independent entry points |
| L1 | 23 | Bronze → Silver transforms |
| L2 | 34 | first-order derivations and assertions |
| L3 | 11 | the compute engines — daily, monthly, period metrics |
| L4 | 4 | `build_screener_universe` and the jobs that read the finished universe |

**This is permission, not instruction.** Nothing in the current schedule
actually runs these in parallel; the levels say what *could* be, and equally
what must not be reordered. The pipeline is sequential today.

One module is in a dependency cycle and is reported rather than linearised:
`capital_raise_tracker.py`. Forcing it into a level would have invented an
ordering the code does not have.

## 5. Reading the layer column

Four values, and the distinctions are load-bearing:

| Value | Means |
|---|---|
| `Bronze` / `Silver` / `Gold` / `Universe` | resolved, writes tables in that layer |
| `out-of-scope` | resolved, writes only `meta.*` or `users.*` |
| `(writes no table)` | resolved, and genuinely writes nothing — a downloader, or a read-only assertion |
| `(unresolved)` | a script is named and did not resolve to a module. Data effects **UNKNOWN** |
| *(blank)* | no script named on the row — a delegated step. Its layer is on the `plan:` row |

Before this was separated, blank carried all of these meanings at once, and
all twenty scheduler rows were blank. A fifth of the run sheet read as "these
jobs touch no data" when the truth was that the lineage graph did not scan
`app/` at all.

## 6. The scheduler jobs

Twenty jobs on cron triggers, from `app/scheduler_registry.py`.
14 resolve to a module and carry real reads and writes; most write only
`meta.job_heartbeat` because the worker delegates its real work to an engine
module invoked separately.

6 do not resolve: `fund_prices`, `anomaly_detect`, `capital_raise_scan`,
`mining_reit_metrics`, `top5_strategy`, `asx_companies`. Their data effects
are **unknown**, not none. Closing that gap means either importing them in
the registry the way the other fourteen are, or extending the parse.

`on_failure` for every one of them is `see job telemetry` — there is no
pipeline to abort and no publication to refuse. A scheduler job that fails
fails alone, and the only evidence is its own telemetry.

## 7. What this document guards against

The run sheet previously carried ten rows named `stage <`, `stage c`,
`stage o`, `stage m`, `stage p`, `stage u`, `stage t`, `stage e`, `stage d`,
`stage >`. Read in order they spell `<computed>`.

`run_plans.py` declares `stages=_DAILY_PRODUCERS + ("composite_score",)`.
`ast.literal_eval` cannot evaluate that, and the parser substituted the
string `"<computed>"` — which the caller then iterated character by
character. The rows had sequence numbers, cadences, statuses and on-failure
text. They read as stages and were letters.

The same fallback hit `required`, making `stage in required` a substring
test: any single-letter stage name would have matched.

Six tests now check that the document is describing the pipeline rather than
its own parse failures — every stage row names a declared stage, no
single-character stage names, no sentinel text published as content, a closed
layer vocabulary, blank carrying one meaning, and a coverage floor so a parse
that silently stops resolving fails instead of passing everything else. The
guard resolves the declared stages *independently* of the generator: if both
read the plans the same wrong way, comparing them would prove nothing.
